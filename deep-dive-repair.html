01

Character controller

Local co-op was a deliberate design choice: sharing the same screen turns coordination into something physical and immediate. Even movement is cooperative — players can throw one another across the submarine, so each robot is both a teammate and a tool.

On the programming side, I built the character controller: the input layer driving two local players, and the custom physics behind everything the robots do — moving, jumping, and throwing. The goal was a controller that felt responsive and predictable, while staying robust enough for a couch session where controllers get unplugged and plugged back in.

Input · New Input System

Two players, hot-pluggable controllers

The controller is built on Unity's New Input System, with a dedicated action map per player so both robots can be driven independently on the same machine.

  • Clean separation between input and gameplay logic through action maps and callbacks
  • Each player is paired to a specific device, avoiding any input mix-up between the two robots
  • Controller reconnection: a pad unplugged mid-game is detected and re-paired to the same player, so a disconnection never breaks the run

Physics · Jump

A jump that feels right

Rather than relying on Unity's default rigidbody behaviour, the jump is driven by hand-tuned physics to get a precise, satisfying arc.

  • Controlled rise and fall, tuned by hand for good game feel
  • Apex and landing weighted so the jump reads clearly and stays easy to aim
  • Consistent height regardless of frame rate thanks to fixed-step physics

Physics · Jump forgiveness

Coyote time & jump buffering

To keep the jump forgiving and responsive, two small timing windows smooth over the gap between what the player intends and what the physics allows.

  • Coyote time: a short grace window after leaving a ledge during which the jump still registers, so a slightly late press never feels punishing
  • Jump buffering: a press made just before landing is remembered and fires the instant the robot touches the ground
  • Both windows tuned to stay invisible — they forgive the player without making the controller feel loose

Physics · Throw

Throwing your partner

A key co-op mechanic: a player can grab and throw the other robot (or objects) across the submarine. The throw is fully physics-driven so the trajectory stays readable and repeatable.

  • Launch direction and force derived from aim and charge for predictable arcs
  • Thrown body handed back to the physics simulation cleanly, with the right velocity
  • Tuned to be useful for traversal without feeling floaty or random

Physics · Throw

Preventing unrealistic throws

Making sure throws follow believable physics and can't take impossible trajectories — no clipping through thin walls or glitching into geometry.

  • Verify the throw angle with a raycast (DrawLine) and a dot product to compute the range, preventing the thrown item from glitching into nearby geometry or being thrown out of bounds

Physics · Gravity

Custom gravity

Each character runs on a custom gravity model instead of Unity's global gravity, giving full control over how the robots fall and how weighty they feel.

  • Per-character gravity tuned independently from the rest of the physics world
  • Stronger fall gravity for a snappier, less floaty descent
  • Single shared knob to balance jump, throw, and fall together as one coherent feel

The Task system

The tasks are the core of the gameplay and therefore held a central place in the game's production. They are the player's only means of action, serving both as a progression mechanic and as a survival system.

Their design had to meet several requirements: be quick to understand, play out smoothly, and allow a natural flow in order to maintain a good gameplay pace. Designing each task required particular attention, as it directly shapes player engagement and the overall balance of the experience.

We wanted a repetitive activity that never became boring. Each task therefore had to take the player a little time — never an instant completion — in order to play against the overall match timer that slowly ticks away. We ended up with 7 different tasks and 1 secondary task.

Each task registers with the TaskManager; the player always interacts with the nearest task, and every task type overrides two methods. 
// Task.cs — base class of every task (press, duo, screwdriver, timing…)
public class Task : MonoBehaviour
{
    [SerializeField] private float playerCheckDimensions;
    [SerializeField] private bool playerInRange;

    void Start()
    {
        TaskManager.GetInstance().taskList.Add(this);
    }

    public void OnDestroy()
    {
        TaskManager.GetInstance()?.taskList.Remove(this);
    }

    public bool playerInRangeMethod(Controller2D player)
    {
        playerInRange = Vector2.Distance(player.transform.position, transform.position) < playerCheckDimensions;
        return playerInRange;
    }

    public virtual void StartInteractingTask(Controller2D player) { }
    public virtual void StopInteractingTask(Controller2D player) { }
}

// TaskManager.cs — returns the nearest task in range of a given player
public Task CheckTaskinList(Controller2D player)
{
    Task taskToReturn = null;
    float taskDistanceToPlayer = 0;
    foreach (Task task in taskList)
    {
        if (task.playerInRangeMethod(player))
        {
            float nearestTaskToPlayer = Vector2.Distance(task.transform.position, player.transform.position);
            if (taskToReturn == null || nearestTaskToPlayer < taskDistanceToPlayer)
            {
                taskToReturn = task;
                taskDistanceToPlayer = nearestTaskToPlayer;
            }
        }
    }
    return taskToReturn;
}

// Controller2D.cs — the interact input just asks the manager
public void Interacting()
{
    Interactingtask = TaskManager.GetInstance().CheckTaskinList(this);
    if (Interactingtask & isGrounded)
    {
        Interactingtask.StartInteractingTask(this);
    }
}

System · Task spawning

Managing task spawning

Tasks disappear once completed — the real challenge lay in their respawn. To keep players moving, we limited the number of tasks on screen and spawned them based on the players' positions, splitting the level into zones.

  • Zone boundaries: each task is assigned a zone from its on-screen position
  • Player detection: the system tracks which zone the players are not in
  • Targeted spawn: a new task appears in a free spot, forcing the players to move to reach it
  • Twofold pressure: constant movement, plus the submarine's health gauge creeping toward zero

Task · Duo

Two-player sync

This task requires both players to be present at the same time. To complete it, they must press the indicated button simultaneously.

  • The most complex task mechanic to pull off
  • Relies on coordination and communication between players
  • Offers a significant reward on success
See the code · TaskSynchroC#
A shared counter tracks the players engaged; the task only completes at 2. 
public class TaskSynchro : Task
{
    public bool isInteracting;
    public Slider slider;
    public TaskSpawner taskSpawner;
    public float _sliderValue;

    private void Update()
    {
        // both players are holding the task → validate it and fill the gauge
        if (CountingSynchro.GetInstance().countingSynchro == 2)
        {
            taskSpawner.DeleteTask(gameObject);
            slider.value += _sliderValue;
            gameObject.SetActive(false);
        }
    }

    public override void StartInteractingTask(Controller2D player)
    {
        if (!isInteracting)
        {
            CountingSynchro.GetInstance().countingSynchro++;
            isInteracting = true;
            player._isRepairing = true;
            player._isActive = false;   // the player is locked in place while holding
        }
    }

    public override void StopInteractingTask(Controller2D player)
    {
        CountingSynchro.GetInstance().countingSynchro--;
        isInteracting = false;
        player._isRepairing = false;
        player._isActive = true;
    }
}

Task · Screwdriver

See the code · Task_RouletteC#
The stick angle is converted to degrees and accumulated frame by frame, so only real full turns in the right direction count. (The screw animation and effects around it were added by the team.) 
public override void StartInteractingTask(Controller2D player)
{
    isInteracting = true;
    Grab = player.GetComponentInChildren<grab>();   // reads the player's aim stick
    playerSelected = player;
}

private void Update()
{
    if (Grab != null)
    {
        angleOfAim = Grab.RotateVector2;
        currentAngle = Mathf.Atan2(angleOfAim.y, angleOfAim.x) * Mathf.Rad2Deg;

        // DeltaAngle handles the -180/180 wrap: a full turn always adds up to 360
        float angleDifference = Mathf.DeltaAngle(previousAngle, currentAngle);
        totalRotation += angleDifference;

        // clockwise is negative: turning the wrong way winds the count back
        if (totalRotation <= -360f * TourAttendus)
        {
            scoreRotation++;
        }
        // … validation, screw animation, VFX
        previousAngle = currentAngle;
    }
}

Task · Washing machine

Charge the ball

Inspired by a washing machine: the player throws the ball into the machine, where it spins for a few seconds before popping back out. While it charges, the player is free to move around.

  • Pays out more, but the ball is locked away while it charges: a real tactical trade-off
  • Tests precision: throwing from afar saves time, at the risk of missing
  • The ball's spin speeds up then slows down, following a sine curve
See the code · Task_CharBallScriptC#
The real ball is hidden and swapped for a spinning copy; when the timer ends, the gauge fills up and the ball is handed back. 
private void OnTriggerEnter(Collider other)
{
    if (other.CompareTag("Ball"))
    {
        other.gameObject.SetActive(false);   // the real ball is "inside" the machine
        isCharging = true;
        FakeBall.SetActive(true);
        playerBall = other.gameObject;
    }
}

private void Update()
{
    if (isCharging)
    {
        timer += Time.deltaTime;
    }

    if (timer >= timeRange)
    {
        timer = 0;
        sliderGlobal.value += sliderValue;
        FakeBall.SetActive(false);
        FakeBall.transform.rotation = initialRotation;
        playerBall.SetActive(true);              // ball handed back
        gameObject.SetActive(false);
        taskSpawner.DeleteTask(gameObject);
        isCharging = false;
    }
    else if (isCharging)
    {
        BallSpining();
    }
}

public void BallSpining()
{
    // elapsed time as a percentage of the total duration
    float elapsedTime = timer / timeRange;

    // smooth spin curve (ease-in, ease-out)
    float spinSpeed = maxSpinSpeed * Mathf.Sin(Mathf.PI * elapsedTime);

    if (FakeBall != null)
    {
        FakeBall.transform.Rotate(Vector3.up, spinSpeed * Time.deltaTime);
    }
}

Secondary Task · Menu · Game state

The computer: launching a level

The in-world computer is the player's gateway into a level: they walk up to it, browse the available missions, and select the one they want to play. Beyond the fiction, this was a piece of UI and menu-navigation work tied to a real game-state change.

  • Fully controller-driven menu: navigate the level list and confirm a choice entirely with the gamepad, no mouse required
  • Selecting a mission switches the game state — from free-roam exploration to an active level — loading the right scene and setup
  • UI feedback (highlight, selection, confirmation) kept clear and readable so both players always know what's about to launch
03

Around the game

Beyond the core gameplay loop, a game is also everything that wraps around it: how a run is introduced, how it ends, and what makes players want to start another one. I handled this layer around the run — the narrative framing, the win/loss flow, and the replayability.

Together, these systems give every session a clear beginning, a clear outcome, and a reason to come back for one more attempt.

Narrative · Level intro

Level intro dialogues

At the start of every stage, a short dialogue scene — inspired by classic JRPG dialogue boxes — sets the tone before the players take control.

  • Traditional dialogue box with text printed letter by letter
  • Characters speaking in turn, advanced at the players' own pace
  • Adds context and personality without slowing the co-op action

Game state · Win / loss

Win, loss & instant restart

Each run ends in one of two game states, both resolving into a clear end screen so players immediately understand the outcome.

  • Win: reaching the safe harbour triggers the victory state
  • Loss: the submarine's health gauge reaching zero triggers defeat
  • Instant restart: a single input relaunches the game, straight back into the tutorial
